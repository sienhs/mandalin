## 6. 배포 시 특이사항 ⚠️

배포가 "성공"으로 끝나고도 조용히 안 되는 자리들이다.

**1) nginx 가 LiveKit 시그널링을 프록시한다 — 미디어는 지나가지 않는다.**
프론트는 Vercel 에서 https 로 뜨는데 AI EC2 에는 인증서가 없다. `ws://52.78.195.46:7880` 을 그대로 주면 브라우저가 mixed content 로 막는다. 메인 EC2 의 인증서를 빌려 `wss://i15d106.p.ssafy.io/livekit` 로 받고 내부에서 평문 ws 로 넘긴다.
- `proxy_pass http://52.78.195.46:7880/;` **끝의 슬래시가 `/livekit` 접두를 뗀다.** 빼면 LiveKit 이 `/livekit/rtc` 를 받고 404 를 준다.
- `LIVEKIT_URL` 끝에 슬래시를 붙이지 않는다 — `livekit-client` 가 `/rtc` 를 이어 붙인다.
- **`proxy_read_timeout 3600s` 필수.** 기본 60초면 조용한 시그널링 소켓을 nginx 가 끊고, 증상은 "통화 중 갑자기 끊김"으로만 보인다.
- 오디오는 브라우저 → AI EC2 **UDP 7882** 로 직접 간다. 보안 그룹에서 이 포트가 막히면 입장은 되고 소리만 안 난다.

**2) `livekit.yaml` 의 `node_ip` 는 반드시 공개 IP 여야 한다.**
없으면 LiveKit 이 사설 IP(172.31.x.x)를 ICE 후보로 광고하고 브라우저는 `could not establish pc connection` 으로 끝난다. 자동 탐지(`use_external_ip`)를 쓰지 않는 이유는 EC2 메타데이터(IMDSv2 hop limit 1)가 컨테이너에서 막힐 수 있어서다. Elastic IP 라 값이 바뀌지 않는다.

**3) AI 쪽 컨테이너는 `network_mode: host` 다.**
WebRTC 미디어가 UDP 이고 포트를 넓게 쓰는데 docker 브리지 NAT 를 한 겹 더 지나면 ICE 후보가 어긋난다. 그래서 `ports:` 매핑이 없다.

**4) worker 의 `AGENT_HTTP_PORT` 를 비우면 기동 즉시 죽는다.**
`start` 모드 기본 포트가 8081 인데 이 호스트는 이전 구성의 `webrtc-sfu` 가 8081 을 점유하고 있고 host 네트워크라 그대로 부딪힌다(`[Errno 98] address already in use`). 그래서 **8099** 로 옮겼다.

**5) CI 의 `rsync` 에서 `.env` 를 반드시 제외한다.**
시크릿은 저장소에 없고 `/opt/mandarin/ai_livekit/.env` 에 상주한다. 빼지 않으면 배포마다 지워지고, compose 가 `${LIVEKIT_API_KEY}` 를 **빈 문자열로 조용히 치환해** 에러 없이 아무도 입장 못 하는 상태가 된다.

**6) `deploy_ai` 잡의 `before_script` 는 비워야 한다.**
`default.before_script` 가 `npm install --global vercel` 인데 AI EC2 러너는 shell executor 라 node 가 없다(같은 이유로 `default.image: node:22` 도 적용되지 않는다).

**7) t3.micro 메모리 — 스왑이 없으면 배포가 죽는다.**
1 GiB 에서 OS·Docker 250MB, 컨테이너 둘 유휴 430MB 를 쓰고 남는 300MB 남짓을 세션(방 하나 ≈ 45MB)과 **배포 피크**(rsync + `pip install`)가 같이 쓴다. `BOT_MAX_CONCURRENT_ROOMS=4` 가 세션은 막지만 배포 피크는 못 막는다 — 증상이 `Killed` 한 줄뿐이라 원인을 찾기 어렵다. `deploy/ec2_swap.sh` 로 2GB 스왑을 붙여 뒀다.
worker 에 `mem_limit: 768m` 을 준 것은 OOM killer 에게 누구를 고를지 알려주기 위한 것이다 — 한도가 없으면 커널이 LiveKit 을 고를 수 있고, 그러면 통화 중인 세션이 **전부** 끊긴다.

**8) `infra/docker-compose.yml` 의 `environment:` 에 없는 변수는 컨테이너에 들어가지 않는다.**
`.env` 에 값을 넣어도 여기 나열되지 않으면 앱이 못 본다. "로컬에서는 되는데 배포에서만 안 되는" 모양으로 드러난다. `TEST_LOGIN_ENABLED` / `TEST_LOGIN_PASSWORD` 가 이 사고로 한 번 걸렸던 자리다.
현재 `DEMO_ENABLED` 는 compose 에 나열되어 있지 않다 — 그래서 `application.yml` 의 기본값 `true` 로 동작한다. **시연 API 를 끄려면 `.env` 만 고쳐선 안 되고 compose 에 줄을 추가해야 한다.**

**9) `ddl-auto` 는 `validate` 다.**
스키마는 Flyway 가 만든다. 엔티티를 고치면 `V10__*.sql` 을 추가한다. prod 는 `flyway.clean-disabled: true` 라 실수로 DB 를 비울 수 없다.

**10) prod 쿠키 설정.**
프론트(Vercel)와 백엔드(EC2)의 출처가 달라 리프레시 쿠키는 `Secure` + `SameSite=None` 이어야 한다(`application-prod.yml`). 또 `server.forward-headers-strategy: framework` 와 nginx 의 `X-Forwarded-*` 헤더가 함께 있어야 카카오 redirect-uri 의 `{baseUrl}` 이 `https://i15d106.p.ssafy.io` 로 계산된다 — 빠지면 `http://backend:8080` 이 되어 카카오 콘솔 등록값과 불일치한다.

**11) Jenkins 는 메인 EC2 의 8080 을 쓴다.**
백엔드 컨테이너의 8080 은 내부 포트라 충돌하지 않는다(외부로는 nginx 443 만).

카카오 로그인 없이 들어갈 수 있는 통로가 있다. `app.test-login.enabled=true` 일 때만 컨트롤러가 등록된다(끄면 404 이고 프론트의 입구도 사라진다).

| 항목 | 값 |
|---|---|
| 엔드포인트 | `GET /api/auth/test/accounts`, `POST /api/auth/test/login` |
| 아이디 | `tester1` / `tester2` / `tester3` |
| 비밀번호 | **`password-d106`** (세 계정 공통) |
| 표시 이름 | 테스터1 / 테스터2 / 테스터3 |
| 친구 코드 | `tester-1` / `tester-2` / `tester-3` |
| 첫 로그인 시딩 | 만다라트 2장, 테마별 건물 9채, **4,500P**, 테스터끼리 친구 관계 |

- 다시 로그인해도 다시 심지 않는다. 초기 상태로 되돌리려면 `users` 에서 `uuid` 가 `tester-1`~`tester-3` 인 행을 지우고 다시 로그인한다.
- 프론트 `/login` 화면에 아이디·비밀번호 입력칸이 나타난다.

**시연용 API**(`/api/v1/demo/**`, `app.demo.enabled=true`): 만다라트 진행률 임의 지정(`PATCH /sheets/{sheetId}/progress`), 과제 진행률 임의 지정(`PATCH /subjects/{subjectId}/progress`), 포인트 임의 지급(`POST /points`), 랜드마크 지급(`POST /buildings/landmarks`). 과제 수행 체크와 포인트 적립이 아직 없어 마을이 자라거나 건물을 살 수 없으므로 발표 기간에 켜 둔 것이다.

> ⚠️ **정식 서비스 전에 `TEST_LOGIN_ENABLED` 와 `DEMO_ENABLED` 를 반드시 `false` 로 바꾼다.** 앞은 비밀번호를 아는 사람이면 누구나 들어오고, 뒤는 포인트를 무제한 지급할 수 있어 상점 경제가 성립하지 않는다. `DEMO_ENABLED` 는 compose 에 줄을 추가해야 실제로 꺼진다(§6-8).

## 9. 기동 확인 체크리스트

```bash
# 1) 컨테이너 상태 (EC2 #1)
docker compose -f ~/S15P11D106/infra/docker-compose.yml ps
#   nginx / backend / postgres / redis / jenkins 다섯 개가 Up

# 2) API 살아 있는지
curl -I https://i15d106.p.ssafy.io/api/auth/test/accounts     # 200

# 3) DB 마이그레이션
docker exec postgres psql -U mandarin_user -d mandarin \
  -c "select version, script, success from flyway_schema_history order by installed_rank"
#   V1~V9 전부 success = t

# 4) 프론트
open https://d106manda.vercel.app

# 5) AI (EC2 #2)
docker ps --format '{{.Names}}\t{{.Status}}'                  # livekit / mandarin-worker Up
docker compose -f /opt/mandarin/ai_livekit/docker-compose.yml logs --tail=50 worker
#   "registered worker" 가 보이면 LiveKit 에 붙은 것
```

| 증상 | 원인 |
|---|---|
| 로그인은 되는데 새로고침하면 로그아웃 | prod 쿠키(`Secure`/`SameSite=None`) 또는 `CORS_ALLOWED_ORIGINS` |
| 카카오 로그인 후 redirect_uri 불일치 | nginx `X-Forwarded-*` 누락 또는 카카오 콘솔 등록값 |
| 프론트에서 모든 API 가 404(HTML 응답) | Vercel `VITE_API_BASE_URL` 미설정 |
| 음성 코치에 입장이 안 됨 | `LIVEKIT_API_KEY`/`SECRET` 세 곳 불일치, 또는 AI EC2 `.env` 유실 |
| 입장은 되는데 소리가 안 감 | EC2 #2 보안 그룹의 **UDP 7882**, 또는 `livekit.yaml` 의 `node_ip` |
| 통화가 1분 남짓 뒤 끊김 | nginx `proxy_read_timeout` |
| 리포트 생성만 실패 | `GEMINI_API_KEY` / `GEMINI_URL` |
| 기동 즉시 `WeakKeyException` | `JWT_SECRET` 이 32바이트 미만 |
