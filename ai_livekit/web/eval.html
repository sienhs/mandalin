프롬프트 평가

개발 도구

evals/golden.jsonl 의 라벨된 발화를 실제 파이프라인에 태워 채점합니다. 실사용 로그는 하루 몇 건이라 어떤 비율도 신뢰구간이 전체를 덮습니다 — 그래서 같은 입력을 정해 두고 반복합니다. 모든 비율에 95% 신뢰구간을 같이 표시합니다.

실행

temperature 를 지정하지 않아 기본값(1.0)으로 돌기 때문에 1회 결과는 흔들립니다. 두 프롬프트 폴더를 견주는 것은 아래 A/B 비교에서 합니다. 같은 것을 CLI 로도 돌릴 수 있습니다: python -m evals.runner --repeat 3

준비 중…

A/B 비교 — 같은 골든셋을 두 폴더로

두 팔의 정확도를 나란히 놓고 눈으로 판정하지 않습니다. 같은 케이스를 둘 다 풀었으므로 케이스별로 짝지어 봅니다 — 판정이 갈린 쌍만 세고 정확 이항검정(McNemar)을 씁니다. 이 규모에서 두 신뢰구간은 거의 항상 겹치기 때문에, 겹침으로 판정하면 실제 개선을 매번 놓칩니다.

백엔드는 위 실행 칸의 값을 함께 씁니다 — 두 팔이 같은 모델로 돌아야 이 표가 프롬프트를 잰 것이 됩니다. 두 폴더를 연달아 돌리므로 시간도 호출도 두 배입니다 — LLM 호출 = 케이스 × 반복 × 2팔 × 2단계(classify·decide). 골든셋 52건을 3회 반복하면 624회입니다. CLI 로는 python -m evals.runner --vs prompts_v2 --repeat 3, 배선만 볼 때는 --provider echo(호출 0회).

정확도 — 점추정과 95% 신뢰구간

intent 혼동 행렬 — 세로 기대 / 가로 실제

요약값보다 이 표가 낫습니다 — 어느 칸으로 새는지가 곧 고칠 문장입니다. goal→chitchat 은 프롬프트가 "가장 흔한 실수" 라고 적어 둔 자리입니다.

비용 · 위반

위반은 정답 라벨이 필요 없는 지표입니다 — 프롬프트가 자기 규칙을 어겨 서버가 잡아낸 횟수입니다.

재실행

고른 것만 다시 돕니다. 판정용이 아니라 분류용입니다 — temperature 기본값(1.0)이라 실패 중에는 프롬프트 문제와 그날 튄 샘플링이 섞여 있습니다. 다시 돌려 통과하면 후자, 또 틀리면 전자입니다. 반복 3회 이상으로 돌리셔야 그 둘이 갈립니다.
