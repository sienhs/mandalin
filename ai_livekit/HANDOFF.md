# 설계 노트

`ai_livekit` 를 고칠 때 먼저 읽을 것들입니다. 사용법은 [README.md](README.md) 에 있고,
이 문서는 그걸 반복하지 않고 **다시 논의하지 않아도 되는 결정**과 **조용히 실패하던
것들**만 적습니다.

## 1. 확정된 결정

| 결정 | 이유 |
|---|---|
| TTS 도입 안 함 | 응답은 텍스트로만. 에이전트가 오디오를 발행하지 않습니다 |
| `AgentSession` 안 씀 | LLM 자리에 3단계 파이프라인이 들어가 맞지 않고, TTS 가 없어 조율할 출력도 없습니다 |
| STT 는 Deepgram | 보낸 오디오 안에서 발화 경계를 자기가 판단하고, 무료 크레딧 $200 에 한국어를 지원합니다 |
| `STT_LANGUAGE=ko` | `multi` 에 한국어가 없어서 일본어나 중국어로 전사됩니다 |
| 마이크 창 15분 | 발화마다 버튼을 누르게 하지 않습니다. 창은 잊고 켜둔 마이크를 끊는 상한일 뿐입니다 |
| 무음은 서버가 거름(`SpeechGate`) | 15분 창은 대부분 무음입니다. RMS 로 무음 프레임을 버리고(발화가 없으면 소켓을 아예 열지 않습니다) 무음이 길면 스트림을 닫습니다 — Deepgram 은 소켓이 열린 시간으로 과금합니다 |
| 브라우저 무음 감지는 **안 씀** | 만들어 봤다가 뺐습니다. 모든 발화가 곧 생성으로 이어지므로 그 자리는 "생성 중 닫기" 가 이미 차지하고 있어 요금이 줄지 않고, 발화마다 버튼을 다시 누르게 됩니다(README "무음 자동 종료는 넣지 않았습니다") |
| 응답 생성 중에는 안 들음 | 그 동안의 발화는 `Conversation` 이 버립니다(락). 전사하면 쓰이지도 않는 오디오에 요금만 냅니다 — `Conversation.busy` 를 게이트가 봅니다 |
| 그 구간을 브라우저도 mute | 최종 전사 시점(= 생성 시작)에 마이크를 끄고 답이 올 때까지 버튼을 잠급니다. 서버만 두면 버려질 오디오를 계속 올려보내고, 생성이 끝나는 순간 STT 스트림이 다시 열립니다 |
| 답이 오면 남은 창을 이어서 재개 | 발화마다 버튼을 누르지 않게 하려는 것입니다. 사람이 멈춘 창·상한에 걸린 창은 재개하지 않고(`resumeAfterReplyRef`), 잠금은 `GENERATION_LOCK_MS`(60초)로 저절로 풀립니다 — worker 가 죽어도 버튼이 잠긴 채 남지 않게 |
| silero VAD 안 씀 | 필요한 판정이 "보낼 만한 소리가 있는가" 뿐이고, t3.micro 에서는 모델이 job 마다 CPU·메모리를 먹습니다 |
| 벡터 DB 안 씀(아직) | 중복 문제의 원인이 아니었습니다(3절) |
| 방은 사용자 1명 + 에이전트 1개 | 백엔드가 방을 `u_<userId>` 로 나눕니다. 그 규칙에만 기대지 않고 겹을 셋 둡니다 — `max_participants: 2`, 발신자 대조, 오디오만 구독(`tests/test_single_user_room.py`) |
| worker 부하 기준을 t3.micro 에 맞춤 | `load_threshold` 0.1(= baseline 0.2 vCPU), 유휴 프로세스 1개, 방 4개. 기본값 0.7 은 baseline 의 7배라 **CPU 크레딧을 태웁니다** — 증상이 청구서뿐입니다(`tests/test_worker_limits.py`) |
| 최종목표는 시트 봉투의 `title` | 모델에게 "첫 목표 발화" 로 추론시키지 않습니다 — 히스토리 창(`BOT_HISTORY_TURNS`)이 두 왕복이면 그 발화가 밀려나 근거가 사라집니다. 서버가 아는 값은 서버가 넘깁니다(`<final_goal>`) |
| 화자 라벨(`Turn.speaker`) 안 씀 | 사람이 1명이라 구분할 것이 없고, 누가 말했는지는 `contents[].role` 이 나릅니다. 표시 이름이 프롬프트에 닿는 경로도 같이 없어졌습니다 |
| `web/` 에 빌드 도구 없음 | `livekit-client` 를 CDN ESM 으로. 정적 파일을 그냥 서빙합니다 |
| 프롬프트 정본은 `prompts/` | 모델에게 가는 텍스트가 코드와 파일로 갈리면 두 곳이 서로 다른 말을 합니다(`tests/test_prompts_are_one_folder.py`) |

파이프라인(`mandarin_goal/`)은 전송 계층을 모릅니다. 새 코드에서 `mandarin_goal.` 을
직접 import 하지 말고 `agent/reuse.py` 를 통하세요 — 다음에 또 옮길 때 고칠 곳이 한
파일이어야 하기 때문입니다. `tests/test_reuse.py` 가 소스를 훑어 이 규칙과 "외부 `app`
패키지를 import 하지 않는다" 를 같이 지킵니다.

## 2. 조용히 실패하던 것들

남은 버그가 아니라 이미 잡은 것들입니다. 각 줄의 테스트가 재발을 막습니다. 여덟 개
전부 에러가 없고 증상이 품질 저하로만 드러나는 종류였습니다. 새로 손댈 때 이 목록을
먼저 읽으세요.

| 증상 | 원인 | 지키는 테스트 |
|---|---|---|
| worker 는 뜨는데 방에 안 들어옴 | 플러그인 import 를 함수 안에 둠. 메인 스레드에서만 등록 가능 | `test_listen.py` |
| 마이크를 껐는데 과금 계속 | `track_muted` 인자 순서. `Participant` 에도 `.sid` 가 있어 예외 없이 빗나감 | `test_event_signatures.py` |
| mute/unmute 반복 후 과금 안 멈춤 | 완료 콜백이 새 태스크를 지움 | `test_transcription_registry.py` |
| 마이크를 눌러도 무반응 | 서버가 음성 불가인데 알리지 않음 | `test_hello.py` |
| 같은 과제가 두 번 담김 | `recommend` 에 담기 버튼. `_STORABLE_ACTIONS` 무시 | 서버 상수는 `mandarin_goal/bot/goal.py`. 버튼 쪽 테스트는 없음 |
| 방금 담은 과제가 중복 검사에서 빠짐 | `subjectId: null` 이라 `to_candidates` 가 버림 | 없음(프론트) |
| 빈도 판별이 안 됨 | 프롬프트의 `"세 가지만 판단한다"` 때문에 모델이 뒤 절을 건너뜀 | 없음. 문구가 근거라 `prompts/classify.md` 를 고칠 때 주의 |
| Spring 시트의 빈도가 통째로 사라짐 | 전송 이름이 어긋남. Spring 은 `period`, AI 는 `frequency` 만 받았음 | `test_sheet_transfer.py` |
| 설명이 카드 밖으로 넘침 | 모델에게 준 길이 상한이 UI·평가 기준과 다름(60자 vs 40자). 스키마에 `maxLength` 가 없어 서버도 안 막음 | `test_output_limits_match.py` |

마지막 줄은 아직 안 터진 상태에서 찾은 것입니다. metadata 를 만드는 곳이
`scripts/dev_server.py` 뿐이었고 거기서 `frequency` 로 적어 두어서, 실서버와 브라우저와
테스트가 모두 통과하면서 Spring 을 붙이는 순간에만 빈도가 사라질 예정이었습니다.
`SubjectRef` 가 `period` 를 정본으로 받고(`mandarin_goal/sheet.py`), `dev_server` 와
`test_sheet_transfer.py` 의 fixture 는 Spring 응답 모양을 씁니다.

공통 교훈이 셋입니다.

1. `smoke_client.py` 가 통과해도 브라우저가 통과한다는 뜻은 아닙니다. 두 번 겪었습니다.
   `--node-ip` 누락(파이썬은 TCP ICE 폴백)과 좌초된 job(파이썬은 매번 새 방)입니다.
   브라우저는 따로 확인하세요.
2. 로그가 셋인데 서로 모르는 게 있습니다. LiveKit 서버 로그는 파이썬 예외를 모르고
   worker 로그는 브라우저 실패를 모릅니다. README 의 "로그가 셋입니다" 표를 보세요.
   worker 는 `worker.log` 에도 씁니다.
3. 대역(fixture, `dev_server`)이 실제 모양을 안 흉내내면 그 대역이 버그를 숨깁니다.
   Spring 자리를 채우는 값은 `GET /api/v1/sheets/{sheetId}` 응답의 필드 이름을 그대로
   써야 합니다. 편한 이름으로 적어 두면 초록불이 계약이 맞다는 뜻이 아니게 됩니다.
   위 표의 마지막 줄이 테스트와 실서버와 브라우저가 다 초록불인 채로 그렇게 숨어
   있었습니다.

## 3. 중복 문제는 벡터 DB 가 아니었습니다

내 시트에 비슷한 유형이 있는데 다시 넣을 수 있다는 문제를 조사한 결과입니다. 로그가
답이었습니다.

```
goal/retrieve 후보 3건: [3, 4, 11]
goal/decide action=recommend '이미 담은 과제와 같은 목표'   ← 검색과 판단 모두 정확
시트 수신 ... 과제=4개                                    ← 그런데 늘어남
```

검색과 판단은 맞았고 프론트가 중복을 만들었습니다(2절의 5, 6번 항목). 벡터 DB 를 먼저
붙였다면 인프라만 늘고 중복은 그대로였을 것입니다. 후보에 아예 없었던 게 아니니까요.
**재기 전에 고치지 않습니다.**

벡터 DB 가 필요해지는 시점은 어휘 자체가 다른 의역이 새기 시작할 때입니다
(`"코테 준비"` 와 `"알고리즘 문제 풀기"`). 갈아끼울 곳은
`mandarin_goal/bot/subjects.py` 의 `search()` 하나이고, 1단계가 만드는 `what` 은 벡터
검색에서도 더 좋은 질의라 버려지지 않습니다.

**그 의역 누출은 검색을 바꾸지 않고 막았습니다.** `<existing_domain_tasks>` 가 칸별로
**담은 과제를 전부** 싣습니다(`_capacity_context`) — 시트가 유계라(칸당 8개,
`sheet.py` 가 자름) 검색으로 고를 이유가 애초에 없었습니다. 검색이 있던 이유는 "다 실을
수 없다" 는 전제였고 그 전제가 틀렸습니다. 실측: 과제 8건 시트에서 유사도 상위 5건은
`코테 준비하기` 를 **버렸고**(바이그램이 0), 전체 목록에는 8건이 다 들어갑니다.
`search()` 는 남습니다 — `<existing_subjects>` 는 **다른 칸까지** 훑어 정렬하는 자리이고,
그쪽 형식이 `subject_id` 지목의 정본입니다.

## 4. 프롬프트 예시는 규칙이 아니라 버그를 가리고 있었습니다

`system.md` 를 11,283자에서 8,865자로 줄인(-21%) 과정입니다. **결론부터 쓰면, 예시
14개 중 4개는 없어도 되고 그것을 빼야 원래 있던 결함이 보입니다.**

### 왜 프롬프트를 줄였나

캐시가 안 걸립니다. worker 로그의 LLM 호출 33회 중 적중은 1회(3%)였고, 그때 값이
`cached=3596` 으로 **입력의 71%** 였습니다. 즉 걸리기만 하면 큰데 거의 안 걸립니다.
명시적 캐싱(`cachedContents`)으로 바꾸면 확률이 아니라 보장이 되지만 **GMS 게이트웨이가
그 엔드포인트를 프록시하지 않습니다.** 남은 길은 프롬프트 자체를 줄이는 것뿐이었고,
`system.md` 의 **49%가 `<examples>`** 였습니다.

### 무엇을 쟀나

`scripts/ablate_prompts.py` 로 예시를 뺀 폴더를 만들고 `evals.runner` 의 짝지은 A/B 에
걸었습니다(62케이스 × 3반복 × 2팔, 갈린 쌍 정확 이항검정, Wilson 95% 구간).
뺀 것은 `generate` 계열 1·2·7·9 이고 **안전 예시(11~14)와 대조쌍(3·4)은 건드리지
않았습니다** — 도구가 그 둘을 지목하면 경고합니다.

| | 원본 | -21% | -21% + 규칙 수정 |
|---|---:|---:|---:|
| intent 정확도 | 100% | 100% | 100% |
| action 정확도(엄격) | 92.86% | 96.43% | 92.86% |
| **출력 정상률** | 100% | **88.71%** | **98.39%** |
| 안전 recall | 100% | 100% | 100% |

가운데 열이 함정이었습니다. 정확도는 **오히려 올랐는데**(갈린 쌍 2건 모두 감축본 승,
원본이 이긴 것 0건) 출력 정상률만 떨어졌습니다(p=0.016). 결함은 전부
`too_long:description` 계열이었습니다.

### 원인은 감축이 아니었습니다

프롬프트가 모델에게 `description 60자` 라고 말하는데 UI 와 평가 기준은 `40자` 였습니다
(2절 표의 마지막 줄). **예시의 짧은 설명이 그 틀린 규칙을 덮어 가리고 있었습니다** —
예시를 빼자 은폐가 걷히면서 원래 있던 버그가 드러난 것입니다.

숫자를 정본(10/25/40/100)으로 고치고 같은 감축본을 다시 돌리자 **결함이 7건에서
1건으로** 떨어졌습니다. 규칙을 60에서 40으로 **더 조였는데 위반이 줄었습니다.**
남은 1건은 `clarify_question` 이고 그 필드의 상한은 원래 맞아 있었습니다.

### 얻은 것과 주의

```
system.md              11,283 -> 8,865자   (-21%)
decide 프롬프트 평균     3,392 -> 2,993 토큰 (-12%, 호출당 약 400)
```

캐싱이 막힌 환경이라 이 절감은 매 턴 그대로 발생합니다.

**두 가지를 적어 둡니다.**

1. 마지막 측정은 **대조군 없이 단독으로 돌렸습니다**(A 팔을 새 규칙으로 다시 돌리지
   않았습니다). 그래서 근거는 "결함 1/62, 정확도가 원본과 소수점까지 같음" 이라는
   **절대값**이고, "통계적으로 동등함을 보였다" 고 말할 수는 없습니다. 정확도 열의
   92.86% 가 원본과 같은 값인 것이 방증이지만 검정을 거친 값은 아닙니다.
2. **예시를 더 빼려면 다시 재세요.** 여기서 얻은 것은 "예시가 필요 없다" 가 아니라
   "규칙이 맞으면 이 4개는 없어도 된다" 입니다. 남은 10개 중에는 대조쌍처럼 정책 분기를
   가르치는 것과 안전 라벨을 가르치는 것이 섞여 있습니다.

리포트는 `evals/ab-round1.json`(A/B)과 `evals/b-round2a.json`(단독)입니다.

## 5. 남은 일

| | 성격 |
|---|---|
| 새로고침 후 시트 유지(localStorage) | `web/app.js` 에 저장·복원 경로가 없습니다 |
| 과제 삭제 | 담기만 있고 빼기가 없습니다 |
| 담은 과제 인계(`postMessage`) | 부모 페이지로 넘기는 경로 |
| React 프론트 이식 | `../frontend/src/components/aiCoach/` 의 `signaling.ts` 와 `sfuClient.ts` 를 버리고 `livekit-client` 로. `taskBoard.ts` 와 패널은 그대로 |
| 인증 | Spring 이 LiveKit access token 을 서명하면 검증은 LiveKit 서버가 하므로 이쪽에 검증 코드가 필요 없어집니다 |
| EC2 배포 | `--node-ip`, 포트, TLS, `--dev` 금지. README "포트" 절 |
| LLM 동시성 제한 | worker 를 여러 개 띄우면 동시 요청도 같이 늘어납니다 |
